# Issue #92 初期Oshiカタログ候補と安全な投入計画

## この資料の位置付け

このIssueでは、公開初期カタログを本番へ投入しない。候補を約100件に確定せず、まず6件の小規模サンプルで、出典・表記・重複・権利・投入手順をレビューできる形にする。

- 候補台帳: [`issue-92-initial-catalog-candidates.yml`](issue-92-initial-catalog-candidates.yml)
- 台帳の6件は人気順ではなく、人物・愛称・ローマ字・複数活動分野・キャラクター粒度を検証するサンプルである。
- 全画像はplaceholderとする。実在画像、個人のProfile・UserOshi・Activity画像は取得・転用しない。
- `db/seeds/development.rb` は予約済みデモアカウントと架空Oshiを整える開発用データであり、この台帳や将来の本番投入には使わない。

## 現行DBで保存できる情報と制約

| 台帳項目 | 現行の保存先 | 制約 |
| --- | --- | --- |
| 正式名 | `oshis.name` | 必須、255文字。同名を許すため一意キーではない |
| 種別 | `oshis.oshi_type` | 既存7種のいずれか |
| 所属・作品 | `oshis.affiliation` | 任意、255文字の単一文字列 |
| 状態 | `oshis.status` | `pending` / `approved` / `rejected` |
| 検索用別名 | `oshi_aliases.alias_name` | 255文字、同じOshi内だけ複合UNIQUE |
| 出典・external ID・投入stable ID | 保存先なし | 台帳と実行結果台帳で保持する。架空のDB列を前提にしない |
| 共通画像の権利情報 | `oshi_common_images` | source、作者、license、帰属、確認日が必須。画像本体の添付とは別 |

`oshis.name` は一意ではなく、外部stable ID用の列もない。したがって名前だけのupsertや、候補台帳だけを頼りにした無人再実行は禁止する。DB変更を行わない最小案では、投入前に各 `stable_id` を「既存Oshi IDへ対応」「新規作成を承認」「保留」のいずれかへ人が確定し、初回適用後のOshi IDを実行結果台帳へ記録する。

新規の初期マスタは、一般利用者の申請と混同しないよう `status: approved`、`created_by_user_id: nil` とする案をレビュー対象にする。これはまだ本番仕様として採用済みではなく、最終候補と投入手順の承認時に確定する。既存Oshiへ対応する候補はstatusや作成者を変更しない。

## 候補レビュー

### 選定基準

1. 正式名、種別、所属・作品を一次資料で確認できる。
2. 別名は公式プロフィールで確認できた愛称・読み・ローマ字だけを候補にする。通称を推測しない。
3. 同一人物の活動分野が複数でも、検索上の都合だけでOshiを分割しない。
4. ブランド、作品、キャラクターの粒度が曖昧なら `hold` にする。
5. 人物・キャラクターの件数配分や「約100件」は、対象市場と運用負荷をレビューするまで確定しない。

### 管理者レビュー結果

候補ごとに次を台帳へ残す。

- 一次資料URL、資料上の識別子、確認日
- 正式名・別名・種別・所属の確認状態
- 既存Oshi検索結果と、同名・表記揺れ・同一人物の判定
- 採用、新規作成、既存IDへの対応、保留、却下
- 画像を採用する場合だけ、権利者／作者、license、source、帰属文、利用条件、確認日

正規化した名前や別名は候補検出にだけ使う。同名を自動統合せず、既存の管理者統合機能を使う場合も対象IDと影響を別途確認する。

## 将来の投入ツールに必要な動作

### 1. 事前確認

実行者は、接続先環境名・DB名・ホスト識別子を表示し、production投入の個別承認内容と一致しなければ停止する。実行前に以下を確定する。

- レビュー済み候補台帳のファイルhashと件数
- 実行者、実行日時、対象環境、対象commit
- stable IDごとの既存Oshi ID／新規作成承認／保留
- `oshis`、`oshi_aliases`、関連する `user_oshis`、`activity_oshis`、`subscription_oshis`、`oshi_common_images` の対象件数
- バックアップの方式、保存先、復元検証、復旧責任者

### 2. dry-run（書込みなし）

dry-runはSQL更新やActive Storage書込みを行わず、次を機械可読な実行結果台帳として出力する。

- 台帳hash、接続先識別情報、開始時刻
- `create_oshi`、`link_existing_oshi`、`create_alias`、`keep_alias`、`conflict`、`hold` の件数とstable ID
- 既存候補のOshi ID、status、完全一致／表記揺れ候補、関連レコード件数
- 255文字超過、未定義種別、重複alias、必須レビュー不足
- 画像は今回すべて `placeholder` であり、blob／attachment／`oshi_common_images` を作らないこと

dry-run後にDBの件数・`updated_at`・候補対応が変わった場合、applyせず再previewする。

### 3. apply

今回のIssueでは実装・実行しない。将来実装する場合は、承認済み台帳hashとdry-run結果を引数にし、PostgreSQL advisory lock等で同じ投入処理の同時実行を防ぐ。

1. stable IDが既存Oshi IDへ対応済みなら、そのIDをロックして名前・状態を再確認する。名前検索で代用しない。
2. 新規作成承認済みなら、最新の重複検索を再実行し、差分があれば停止する。新規マスタのstatus・作成者方針も承認済み値と一致させる。
3. Oshiとaliasesを1トランザクションで追加する。既存の管理者編集を自動上書きしない。
4. 成功時にstable IDと確定Oshi ID、作成したalias ID、台帳hashを実行結果台帳へ保存する。
5. 一部失敗時はトランザクションをrollbackし、成功件数として記録しない。

対応表のない2回目のapplyは拒否する。対応表がある再実行は、対象IDと現状が初回結果どおりならno-op、後から変更されていればconflictとして停止する。

## 競合・中断・復旧

- **同時実行**: 投入単位の排他lockと対象Oshi行lockを使う。lock取得失敗時は待ち続けず停止する。
- **中断再開**: commit済みの実行結果台帳から再開し、未記録の名前一致を「作成済み」と推測しない。
- **後編集**: 管理者が後から変更したname、affiliation、status、aliasesを投入ツールが上書きしない。
- **単純削除禁止**: 投入後にUserOshi、Activity、Subscription、共通画像が関連したOshiは削除しない。管理者統合または個別の是正計画を使う。
- **全バックアップ復元の限界**: 全DB復元は投入後の正当な新規データも失う。復元は障害範囲と時点を確認し、個別補償か全体復元かを別途承認する。
- **画像**: 将来画像を扱う工程は #86/#87 の管理者CRUDと権利検査を使用する。カタログ投入ツールが任意URLをfetchしたり、共通画像を直接作成したりしない。

## 検証計画

本番適用前に、productionと分離した専用test DBで合成候補を使い、次を検証する。

1. dry-runがDB・Active Storageを変更せず、件数と差分を正しく出す。
2. 初回apply後の実行結果台帳が全stable IDとOshi IDを持つ。
3. 同じ台帳・対応表で再実行するとno-opになる。
4. 既存同名、同一alias、他Oshiの同じalias、本人pending、rejectedをconflict／review対象として出す。
5. 途中例外でOshiとaliasesがともにrollbackされる。
6. 2プロセス相当の同時実行で二重作成しない。
7. apply後に管理者編集したレコードを再実行が上書きしない。
8. 検索、本人pending、管理者承認・統合、共通画像無効化の既存回帰を通す。

## 本番投入前の承認ゲート

以下を一括確認するまでproductionへ接続・書込みしない。

- 最終対象リストと件数（約100件を既定値にしない）
- 全候補の重複・粒度・表記レビューと、stable ID→Oshi ID対応
- 実在画像を採用する場合の権利・帰属一式。未確認画像はplaceholder
- 投入ツールのコードレビュー、test結果、台帳hash、dry-run結果
- 接続先、実行者、実行時間帯、排他方法、監視担当
- バックアップの実在・復元試験と、復旧判断者・復旧手順

このゲートの承認は、本Issueの文書作成承認とは別に取得する。
