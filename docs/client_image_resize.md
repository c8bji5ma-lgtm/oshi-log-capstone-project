# 端末側の画像縮小

プロフィール画像、推しの代表画像、画像ライブラリ、活動画像では、選択した画像がサーバーの上限（10 MiB、最大辺2560px、500万画素）を超える場合に、ブラウザー内で送信用コピーを縮小する。

## 処理方針

- JPEG・PNG・WebPだけを対象とし、HEICやアニメーション画像など既存の非対応形式は受け付けない。
- 上限内の画像は同じ `File` を使用し、再エンコードしない。
- 超過画像は1枚ずつ処理し、すべて成功した場合にだけ入力を送信用コピーへ差し替える。途中失敗時は選択全体を解除し、巨大な原本や一部だけを送信しない。
- 端末の元ファイルと保存済み画像は上書き・削除しない。サーバー側の形式、容量、寸法、画素数検査も必須とする。
- 選択変更時は古い非同期処理結果を破棄し、処理中はフォーム送信を無効にする。
- 初回デコード前に25 MiBを超えるファイルを拒否する。この上限はブラウザーのメモリ安全を保証するものではなく、デコード失敗時は端末での縮小と再選択を案内する。

## 出力と画質

- JPEGとWebPは元の形式を維持し、品質0.90、0.82、0.74、0.66の順で10 MiB以下を試す。それでも超える場合は寸法を段階的に下げる。
- PNGは透過を維持するためPNGのまま出力し、10 MiBを超える場合は寸法を段階的に下げる。透過画像を自動でJPEGには変換しない。
- EXIFの向きをデコード時に反映し、向きが二重適用されない送信用画像を作る。
- Canvasによる再エンコードではEXIFやICCなどのメタデータが保持されず、色味や細部が変わる可能性がある。原本は変更しない。
- 出力後にMIME、バイト数、寸法、画素数を再検査する。

## 検証範囲と残る確認

自動テストではChrome上で、無変換、縮小、JPEG、透過PNG、EXIF向き、複数選択の全件取消、選択競合、保存後の画像を確認する。任意サイズの画像を安全にデコードできることや、端末ごとの色再現・メモリ消費は保証しない。

iPhone Safariでは次を実機確認する。

1. 12 MP級の縦向き・横向き写真を選択し、表示方向と四隅の切り取りが正しいこと。
2. 低メモリ状態でも、失敗時に送信されず再選択案内が表示されること。
3. 写真の色味と細部、および透過PNG/WebPの透明部分を目視確認すること。
4. 複数選択の途中失敗、選択取消、処理中の再選択で古い画像が送信されないこと。
5. 縮小後の送信とサーバー側再検査が成功すること。
